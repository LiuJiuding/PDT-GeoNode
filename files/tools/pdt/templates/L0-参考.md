# L0 最小规范：写作参考

> **这份是参考，不是规范，也不是 L0。** 它讲"怎么写 `spec/*.md`"，本身没有决定权。
> 规则的所有权在 `../../spec/README.md`；三层分工与流程在 `../../docs/10-文档分层与协作规范.md`。
> 你（架构师）改 L0；agent 不改 L0，只改 L1（`docs/manual/**`）、测试与实现。
> 本文件由 agent 维护；发现与 `pdt_spec.py` 行为不符，以那个脚本为准并让我改这里。

现成的三份 L0：`spec/node_info.md`（`MMB-1…10`）、`spec/viewer_overlay.md`（`EVO-1…7`）、
`spec/pdt_selection.md`（`PDS-1…13`）。**照抄现有那份最像的**，比从零写快得多。

## 1. 机械规则（`pdt_spec.py` 真正校验的东西）

| 规则 | 后果 |
| --- | --- |
| 文件名 `spec/<主题>.md`；`README.md` 与 `coverage.md` 除外（层自身的簿记） | 其它 `.md` 一律被当成 L0，**所以别往 `spec/` 放参考/草稿**（会报"no `**ID**` items found"） |
| **前 3 行**里必须有 `<!-- owner: user; agent: read-only -->` | 缺了报"first three lines must carry…" |
| 不变量写成行首粗体 ID：`- **PDS-9** …` | 解析器只认这个形状；ID 大小写不敏感（`[A-Za-z][A-Za-z0-9]*-\d+`） |
| 每个 ID 在 `spec/coverage.md` 里有一行 | 缺行 = "no row in coverage.md"；多行 = "has a row but … no such item" |
| 覆盖行的 L1 路径/锚点/测试名必须真实存在 | 锚点按 GitHub 风格 slug（中文保留），失效即警告 |
| 覆盖行的状态写 `待补` 就是缺口 | `check` 会报 "still a gap"，`--strict` 直接失败 |
| L0 内容哈希变了 → 提醒"决定改了，L1/测试要跟进" | 跟进完跑 `python tools\pdt\pdt_spec.py sync` 刷新 |
| **段落标题不被校验** | 五段是惯例；只写 `## 不变量` 也能通过（解析器只看归属标记与 `**ID**`） |

命令：

```powershell
python tools\pdt\pdt_spec.py list      # 每条 ID 落在哪
python tools\pdt\pdt_spec.py check     # 建议性（默认退出码 0）
python tools\pdt\pdt_spec.py check --strict
python tools\pdt\pdt_spec.py sync      # 核对完 L1/测试后刷新哈希
```

篇幅与内容预算（`spec/README.md` 定）：**一主题一页 ≤ 60 行**；只写"决定"，
不写实现机制、代码路径、实测数字、坑与历史、算法细节。判断标准一句话：
**改这一行，会不会需要 agent 跟着改实现？会 → 它属于 L0；不会 → 属于 L1/L2。**

## 2. 可复制骨架

放到 `spec/<主题>.md`，把 `TAG` 换成你的主题前缀（如 `PDS`、`EVO`、`MMB`）。

```markdown
<!-- owner: user; agent: read-only -->
<!-- 条目格式见同目录 README.md：不变量一行一条，ID 写在行首粗体里。
     本文件初稿由 用户 依 docs/10-文档分层与协作规范.md 的示例落成（YYYY-MM-DD），
     之后由用户维护；agent 只在回复里提建议，不直接改。 -->

# <主题> 最小规范

> 细则与例子在 `../docs/manual/<路径>.md`，实测与坑在 `../docs/0X-<...>.md`。
> 两份都不具有推翻本文件的效力。

## 目标
一句话：这东西为什么存在（用户视角，不是实现视角）。

## 契约
- **触发**：谁在什么条件下产生什么。
- **输入**：从哪读到什么（可空/默认值）。
- **输出**：产出什么、写到哪里。
- **持久化**：存不存、存在哪、旧文件怎么办。

## 不变量
- **TAG-1** …
- **TAG-2** …

## 验收
- 无头：`tools\pdt\tests\<test>.py` 全绿。
- 真窗口（如需要）：`<gui_table>.py` 全绿 + 必须在**用户配置**下跑。
- 现场（如需要）：`qa\<probe>.py` PASS。

## 明确不做
- …（有意**不做**的事；写"不做"，不写"暂不支持"）
```

小贴士：
* 想加一句"为什么"（给人看的理由）——放引用块或 L1，别塞进不变量里（见 §5）。
* 标题顺序随意，但**同一份文件里的 ID 顺序就是实现的顺序**，新条目**追加**，不要插在中间（`Domain` 那种"菜单顺序 = 存储值"的东西尤其如此）。
* 2026-09-14 起**只有五段**：原先单列的 `不可协商的边界` 已取消，那类内容并入 `明确不做`。

## 3. 五段各自要回答的问题

| 段落 | 只回答 | 别写 |
| --- | --- | --- |
| 目标 | 为什么存在（一句话） | 怎么做、代码在哪 |
| 契约 | 触发/输入/输出/持久化 | socket 名之外的类型细节、算法 |
| 不变量 | **可判定的性质**，一行一条 | 理由、历史、实测值、实现手段 |
| 验收 | 能复现的命令 + 判据 | 泛泛的"测试通过" |
| 明确不做 | 有意**不做**的事 + 明确排除的行为 | "以后可能"的规划 |

## 4. 从现有 L0 学到的具体写法

**① 契约写"触发/输入/输出/持久化"四件事**（`node_info.md`）：
"按住快捷键显示 → 松开消失" / "当前编辑的节点树 + 光标位置" / "跟随光标的只读信息块" /
"无：不改节点、不改几何、不改选择、不写文件"。**"无"也是契约的一部分**，写出来才能验收。

**② 不变量里可以直接写用户可见的默认值**（`viewer_overlay.md` 的 EVO-3/4/5/6）：
单位（世界单位）、倍数（1 × 用户缩放）、默认颜色（黄色）、上限（1,000,000）、
退化值不画。**数值是可以进 L0 的**——因为它决定"看起来对不对"，agent 照着实现。
反过来"实测 1006.6 s / 峰值 5.5 GB"这种**测量结果**属于 L2。

**③ "引用哪份细则"别放进不变量**。`MMB-5` 里那句
"信息块的排布参考 `./node_info_ui_v3.png`"是 L0 该有的（**判据是那张图**）；
而"实测见 archive §13"是 L2 指针，更适合放在文件头引用块。

**④ 验收要写清"在什么配置下跑"**。`node_info.md` 的验收里"含 GUI 测试**必须**在用户配置下跑"
是一条**决定**（因为 agent 默认会 `--factory-startup`，那样发现不了 UI 缩放的 bug）。

**⑤ 段落已统一（2026-09-14）**：四份 L0 现在都用
`目标` / `契约` / `不变量` / `验收` / `明确不做`；旧的 `## 边界`、`## 不可协商的边界`
都已改名并把内容并入 `## 明确不做`。解析器仍不校验标题，但**新条目一律用这五个**。

**⑥ 已知的不一致（待你决定，不改也行）**：`viewer_overlay.md` 仍只有
目标/不变量/验收/明确不做（没有"契约"段），`pdt_selection.md` 与 `selection_pick.md` 是五段齐全。
这是历史差异，不影响校验。

## 5. 好例子 / 坏例子（同一件事的两种写法）

| 坏（不可判定 / 越界） | 好（可判定 / 属 L0） |
| --- | --- |
| "选择要快" | "元素数超过 1,000,000 时什么都不画，只允许一行提示文字"（EVO-6 的写法） |
| "命中判定要准" | "同一批探针点必须与编辑器自己的点击判定逐点相同，UI 缩放不是 100% 时同样成立"（MMB-2） |
| "索引超过范围就报错" | "越界序号不是错误，只是匹配不到任何元素"（PDS-7）——**把"不是错误"写死**，agent 才不会替你报错 |
| "优先用 socket 实现" | 删掉：那是实现（写在 L1/L2）；如必须约束（例如"不许动 DNA"）就写成**边界** |
| "拾取器应该也知道组名" | "拾取器的预选只需要满足 预选集合 ⊆ 节点选择集合"（PDS-13）——把**上下界**写清楚，而不是要求复刻实现 |
| "支持常见的几种情况就够了" | 逐条列出：`Domain` 有哪几个值、各自对应哪个组件（PDS-9） |

一条不变量如果**没法用一个测试或一次现场测量确认**，它就不是不变量（`spec/README.md` 原话）。

## 6. 覆盖表（`coverage.md`）的契约

这部分是 **agent 维护**的；你只管写 L0，ID 出来之后我来接：

```markdown
## spec/<主题>.md
l0_sha1: <由 pdt_spec.py sync 刷新>

| L0 条目 | L1 章节 | 测试 | 状态 |
| --- | --- | --- | --- |
| PDS-9 | docs/manual/nodes/pdt_selection.md#domain元素种类 | test_pdt_selection.py, test_selection_instances.py | 已覆盖 |
| PDS-11 | docs/manual/nodes/pdt_selection.md#限制 | — | 仅文档 |
```

* **L1 章节**：相对 `tools/pdt/` 的路径 + `#锚点`（锚点 = 标题按 GitHub 规则 slug 化，中文保留）。
* **测试**：`tests/` 下的文件名，多个用逗号分隔；没有测试就写 `—`。
* **状态**：`已覆盖` / `仅文档` / `待补`（`待补` 会让 `check --strict` 失败）。
* 你**不需要**碰这张表，也不用记格式；只要 ID 不改，我照 ID 续行。

## 7. 你改 L0 之后会发生什么（一次提交里完成）

1. 我读 L0 的 diff，列出**受影响的 ID**（新条目 = "新增条目"）。
2. 我把 L1 细则（`docs/manual/**`）改成与之一致——**手册与 L0 冲突时改手册与实现，不动 L0**。
3. 我补/改测试（每一条不变量至少一条断言；`test_manual_examples.py` 会逐行执行手册里的例子表）。
4. 我更新 `coverage.md`，跑 `pdt_spec.py check --strict` 到 0 警告，再 `sync` 刷新哈希。
5. 有 C++ 改动就走构建与 `run_tests.ps1`；纯 Python 只需 `sync_addons.ps1`。
6. 提交时 **L0 单独一笔**（护栏②的纪律：`spec/**` 不与其它路径混在同一笔提交里）。

如果 L0 缺条目、含糊或自相矛盾：我**不改**，在回复里列"建议 L0 增补/澄清 N 条 + 推荐措辞"，由你落笔。

## 8. 常见坑（都踩过）

| 坑 | 现象 / 后果 |
| --- | --- |
| 往 `spec/` 放参考、草稿、"旧版备份" | 被当成 L0：报"no `**ID**` items found"，或混进 `list` |
| 忘了归属标记或写到第 4 行 | `check` 直接报，护栏①的输入 |
| ID 插在中间 / 改 ID | 旧 ID 的覆盖行变成"no such item"；**ID 是稳定引用，只追加不改名** |
| 把"实测数字/坑/代码路径"写进不变量 | 你的 60 行会越写越长，且每次改动都要跟 L1/L2 对账 |
| 条目含糊（"尽量准确"） | 我无法为它写断言 → 覆盖表只能标 `仅文档`，等于没有可验收的保证 |
| L0 与 L1 冲突时想改 L0 | **不动 L0**：L0 是你的决定，要改由你改，我只提建议 |
| 同一主题拆成两份 L0 | 覆盖表按文件分段，条目必须全局唯一（`PDS-1` 只有一个出处） |
